  ## Context                                                                    
  `cocoindex-code` (https://github.com/cocoindex-io/cocoindex-code) is a        
  semantic code-search CLI built on the CocoIndex Rust engine. Today it stores  
  chunk embeddings in **SQLite via the `sqlite-vec` extension (`vec0` virtual   
  table)**. The `vec0` KNN is **exact brute-force** (O(n) linear scan over all  
  chunk vectors per query), so query latency grows linearly with codebase size. 
                                                                                
  Goal: replace the storage/query backend with one that has a real **HNSW       
  approximate-nearest-neighbor index** so query latency becomes sublinear.      
  Target deployment: a **single codebase, indexed once and updated              
  incrementally, served read-only over streamable-HTTP MCP to 100+ concurrent   
  users. (could be launched when daemon is launched)**                          
                                                                                
  Chosen backend: **LanceDB**, embedded in-process (it's a CocoIndex built-in   
  target, supports HNSW, needs no separate server, and supports concurrent      
  reads). This preserves the tool's zero-config/embedded nature. (If a          
  `--backend qdrant` shared-server variant is requested instead, see the        
  "Qdrant variant" section at the end.)

  Key finding from reading the actual CocoIndex 1.0.7 LanceDB connector source
  (.venv/.../connectors/lancedb/_target.py):

  - The CocoIndex LanceDB target only does table DDL + merge_insert
  upserts/deletes + a periodic table.optimize(). It does not create any vector 
  index — there is no HNSW/IVF creation anywhere in the connector. So the
  prompt's assumption that "CocoIndex sets the HNSW index" is wrong. To get
  HNSW, our code must call LanceDB's table.create_index(...) ourselves (after
  the first index build / on a reindex hook). That's doable but it's an extra
  moving part the prompt didn't account for.
  - Incremental indexing is preserved for free: merge_insert is keyed on the
  primary key and CocoIndex fingerprints each row in reconcile, and process_file
  is @coco.fn(memo=True) — so only changed chunks re-embed. Good.
  - The connector ships under cocoindex[lancedb] (needs lancedb + pyarrow),
  which is not currently installed — it's an extra.
  - The vector dimension flows from the existing embedding: 
  Annotated[NDArray[float32], EMBEDDER] annotation (EMBEDDER acts as the
  vector-schema provider), so dimension stays non-hardcoded. Good.
  - The connector gives no query/search helper — the read path must talk to

      726 +## Vector Search Backend (LanceDB + HNSW)

      728 +Chunk embeddings are stored in an embedded **[LanceDB](https:/

          +separate server — so the tool stays zero-config, while support
          +ing concurrent reads for the MCP server.                      
      729 +                                                              
      730 +**Approximate nearest-neighbour (HNSW).** Once a codebase grow
          +s past a few hundred chunks, the embedding column is indexed w
          +ith an **HNSW graph using cosine distance**. HNSW makes query 
          +latency *sublinear* in codebase size, versus the previous exac
          +t brute-force scan that grew linearly. The index is built auto
          +matically after indexing and maintained incrementally on subse
          +quent updates.

      732 +- **Small indexes** (below 256 chunks) skip the ANN index enti
          +rely and use LanceDB's exact flat scan — it's already fast at 
          +that size and avoids approximation.                           
      733 +- **HNSW is approximate**, so recall is < 100%. The defaults (
          +`m=20`, `ef_construction=300`, query-time `ef=128`) are chosen
          + to keep recall very close to exact for typical top-k code sea
          +rch. These live in `cocoindex_code/lancedb_store.py`.

      735 +**Scoring.** Results carry a `score` that is cosine similarity
