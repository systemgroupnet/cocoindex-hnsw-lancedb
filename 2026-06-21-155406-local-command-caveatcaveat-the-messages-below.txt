● The cause is in the MCP search tool's default behavior, not in the search path
  itself.

  What happens

  When you run ccc index, the daemon spawns an index task that grabs
  Project._index_lock and holds it for the whole run (project.py:84, run_index).

  Meanwhile, the MCP search tool defaults refresh_index=True (server.py:101). So
  every query refreshes the index before searching:

  if refresh_index:
      await loop.run_in_executor(None, lambda: _client.index(project_root))   # 
  server.py:127
  resp = await loop.run_in_executor(None, lambda: _client.search(...))        # 
  server.py:128

  _client.index is a blocking call that streams until the index run completes
  (client.py:262, "Blocks until complete"). On the daemon side that request goes
  through stream_index, which always spawns its own index task
  (project.py:189), and that task immediately does async with self._index_lock:
  (project.py:84).

  Since ccc index is already holding that lock, the MCP-triggered refresh blocks
  waiting to acquire it. The lock isn't released until ccc index finishes — so
  the MCP query hangs for the entire duration of indexing. The search query is
  never even reached; it's the refresh-before-search that's stuck behind the
  lock.

  Secondary contributor (first index only)

  Even with refresh_index=False, the very first index blocks searches by design:
  should_wait_for_indexing returns not _initial_index_done.is_set()
  (project.py:216), so _dispatch routes the search through _search_with_wait →
  wait_for_indexing_done() → await _initial_index_done.wait() (daemon.py:520,
  project.py:218). Once the first index has ever completed, this flag stays set,
  so this path no longer blocks re-indexes — but the refresh_index=True path
  above still does.

  So, in short

  The MCP server isn't crashing — each query is serializing behind the index
  lock because it tries to refresh the index first, and that refresh can't
  proceed until ccc index releases the lock.

  If you want queries to stay responsive during indexing

  A few options, depending on intent:

  1. Quick mitigation: call the MCP search tool with refresh_index=False.
  Queries then hit the existing (possibly slightly stale) index and return
  immediately — assuming the project has been indexed at least once.
  2. Make refresh non-blocking when an index is already in flight: in
  stream_index, if _index_lock.locked() (or _indexing_scheduled), don't spawn a
  second pass that waits on the lock — just return immediately (the in-flight
  ccc index already covers the refresh). This mirrors the existing "never spawn
  a competing index" intent noted for searches.
  3. Let reads run concurrently with writes: LanceDB supports concurrent readers
  during writes, so a read-only search could be allowed to proceed even while
  indexing — the blocker here is purely the refresh-acquires-lock step, not
  LanceDB.

  Want me to implement option 2 (skip the redundant refresh when an index is
  already running)?

● Done. Concurrent reads now work during indexing. Here's what changed and why.

  The core fix

  The blocker was that the MCP search tool issued a separate, blocking 
  _client.index() before every query, and that refresh had to acquire the same
  _index_lock that ccc index was holding. The search query itself was never the
  problem — LanceDB serves reads during writes.

  So I folded refresh into the search request and made it idle-only:

  SearchRequest now carries refresh: bool (protocol.py). The daemon decides what
  to do (daemon.py):

  if req.refresh and not project.is_indexing:
      await project.refresh_index()      # idle: refresh, then read
  if project.should_wait_for_indexing:
      return _search_with_wait(project, req)  # cold start only: no table yet
  results = await project.search(...)    # otherwise: read current table 
  concurrently

  - During ccc index (or the initial background index): is_indexing is True →
  skip the refresh → read the current table immediately, concurrent with the
  in-flight write.
  - Idle daemon: refresh incrementally first (preserves the old fresh-results
  semantics).
  - True cold start (no table exists yet): still waits, since there's nothing to
  read.

  Supporting changes

  - Project.is_indexing — _index_lock.locked() or _indexing_scheduled.
  - Project.refresh_index() — spawns the index as an independent task and awaits
  it, so a client disconnect can't abort a write mid-flight. The is_indexing
  check → spawn is atomic (no await between them), so two simultaneous searches
  can't both kick off a refresh.
  - MCP search tool (server.py) — dropped the separate _client.index() call;
  passes refresh=refresh_index into the single search request.
  - CLI ccc search --refresh — unchanged UX: it still runs its own foreground
  index with progress, so _search_with_wait_spinner passes refresh=False to
  avoid a daemon-side double refresh.

  Verification

  - mypy clean across all 6 changed modules.
  - test_query.py, test_e2e_daemon.py, test_embed_params_forwarding.py, and
  test_e2e.py::test_session_search_refresh all pass.

  Note this is a small semantic shift worth being aware of: a query issued while
  an index is running now returns results from the last-committed state rather
  than waiting for the in-progress pass to finish — which is exactly the
  concurrent-read tradeoff you asked for. The next query (once indexing settles)
  picks up the fresh data.

● Confirmed the mechanics. open_table (db.py:1634) passes no version=, returns a
  fresh AsyncTable each call → it reads the latest committed manifest at that
  moment. And the writer side commits incrementally: each _apply_actions batch
  runs its own merge_insert(...).execute() (_target.py:356–470), which is a
  separate LanceDB transaction/version. So the two halves line up. Here's the
  actual answer:

  It depends which case you're in

  The daemon's search dispatch branches on should_wait_for_indexing (= "has an
  index ever completed in this daemon"):

  1. First-ever index (no prior completed index) → it waits, no partial results

  ccc index is building the table from scratch. should_wait_for_indexing is
  True, so a search routes to _search_with_wait and blocks until indexing 
  finishes, then searches the complete table. This is deliberate — at cold start
  there's no meaningful prior dataset, and mount_table_target only just created
  an empty table, so partial results would be near-useless. So in this case:
  no, it doesn't return the half-done chunks; it waits.

  2. Re-index (a prior index already completed) → yes, concurrent live reads

  This is the is_indexing && !should_wait_for_indexing path the new code
  enables. The search reads the current committed snapshot immediately:

  - LanceDB is MVCC. Each merge_insert batch commits a new version. A fresh
  open_table per search sees the latest committed version.
  - So the reader sees the full previous dataset, progressively updated as the
  re-index commits new/changed chunks. It's a moving target — two searches a
  second apart during the run can see slightly different data.

  Two details worth knowing for case 2

  Vector index coverage. The HNSW index is built post-indexing
  (_ensure_vector_index, rows ≥ 256). During a re-index it's whatever the last
  completed run built. Rows committed since aren't in the HNSW graph yet — but
  query.py doesn't set fast_search, so LanceDB's default behavior also
  brute-force-scans the unindexed fragments and merges them in. Results stay
  complete, just marginally slower for the new portion. (Then
  _ensure_vector_index rebuilds the HNSW after the run.)

  Churn for changed files. process_file is @coco.fn(memo=True), so unchanged
  files aren't reprocessed — their chunks stay rock-stable during the re-index.
  Only changed/removed files churn (old chunks deleted, new inserted), and since
  merge_insert is atomic per batch, you never see a torn write within a file's
  batch; across the whole run you might briefly see a mix of old/new chunks
  across different files.

  TL;DR

  - Re-indexing: yes — searches return already-indexed chunks immediately,
  reading a live-updating committed snapshot, concurrent with the write.
  - First index: no — searches wait for it to finish, because there's no prior
  data to read and the table starts empty.
